# AnimeVault Android — Full Mobile Bug Bounty Audit

**Scope and method.** Static, build, and generated-project audit of the Android-specific React/Capacitor bundle on 2026-09-09. I traced the mobile entry point, route dispatcher, auth and recovery paths, storage, player, styles, Capacitor configuration, native patch generator, and release workflows. No device/emulator, production account, database, or secrets were used; findings that require a runtime/provider response are labelled **LIKELY** rather than asserted as observed. No source, database, workflow, or production configuration was changed.

## 1. Executive Summary

**Production readiness: NOT READY.** There are **22 unique findings**: **P0 0, P1 7, P2 9, P3 4, P4 2**. Eight are security findings. Confidence: **15 confirmed, 6 likely, 1 possible**. The Android app cannot currently deliver the stated Movies/Dramas/TV product reliably: Movies/TV detail routes lose their route parameters, the expected standalone movie/TV watch routes are not mobile routes, and the active Movies/TV player is an unprotected third-party iframe embedded inside the details route.

The most urgent blockers are: broken Movies/TV details navigation, no `/watch/movie/:id` or `/watch/tv/:id` mobile implementation, external/OAuth navigation being globally cancelled, an exposed TMDB credential, recovery OTP persistence, missing Android lifecycle integration, and a release pipeline that generates separate Android and desktop releases rather than one release.

## 2. Mobile Architecture

* **Entry/root:** `src/mobile/index.html` → `src/mobile/main.jsx`, a React 18 `HashRouter`, React Query, `UserProvider`, global `SubAccountGate`, desktop `ErrorBoundary`, notification bridge, and `AppMobile`.
* **Router:** `AppMobile` is a hand-written pathname `if/else` dispatcher rather than `<Routes>`. Unmatched paths render the desktop `App`, which itself mounts another `SubAccountGate` and desktop navigation/layout.
* **Primary mobile shell:** top bar + drawer + `<main class="av-v2-content">`; no persistent mobile bottom navigation is rendered by `AppMobile`.
* **Content:** `DramasMoviesPage` is the intended home; `SearchPage` uses direct TMDB calls; `DramaDetailPage` supplies Movies/TV details and an iframe player. `AndroidVideoPlayer` exists but is not imported by any route/player.
* **Auth/data:** the mobile bundle imports shared `UserContext`, Neon auth client, legacy proxy/session/database layers, and localStorage. Sub-profiles are shared `SubAccountGate`/`subAccounts` utilities.
* **Native/build:** Capacitor webDir is `dist-mobile`; Android is generated in CI. The native ad-blocker is generated by `scripts/patch-android-adblock.cjs` before `cap sync`; Android deep linking/signing are injected by workflow shell/Python code.

## 3. Production Readiness

**NOT READY.** Functional blockers are MOB-001, MOB-002, MOB-003, MOB-004, MOB-005, MOB-006, and MOB-007. Security and privacy blockers are MOB-008, MOB-009, MOB-010, MOB-011, MOB-012, MOB-013, and MOB-014. Build/release blockers are MOB-018 and MOB-019. A successful desktop Vite build does not test the mobile bundle, sync an Android project, compile native Java, or exercise Android lifecycle/back/deep links.

## 5. Complete Bug Database

### MOB-001 — Movie/TV detail route drops all route data
**Severity:** P1  
**Category:** BUG, MOBILE, NAVIGATION  
**Confidence:** CONFIRMED  
**Platform/route:** Android; `/drama/:id`  
**Component/file:** `MobileDramaDetails` / `src/mobile/AppMobile.jsx`; `DramaDetailPage.jsx`

**Description / steps:** From Home or Search, tap a Movies/TV card. Those pages call `navigate('drama-detail', { id, mediaType, title })`; `mobileNavigate` converts it to `/drama/:id`. The `/drama/:id` branch renders `<MobileDramaDetails/>`, but that wrapper calls `<DramaDetailPage id={undefined}>` because it does not use `useParams` or forward `params`, `goBack`, or `navigate`.  
**Expected / actual:** A fetched title detail screen / deterministic “Missing movie or TV show ID.”  
**Root cause/evidence:** Route state is discarded twice: the path contains `id`, then the wrapper ignores it; `DramaDetailPage` only reads `params?.id`.  
**Impact:** Core discovery-to-detail conversion is broken.  
**Recommended fix:** Use a real route definition or `useParams`, derive media type from a validated route/query field, and pass navigation callbacks.  
**Regression risk:** High; test Home, Search, Library, deep links, back, movie and TV IDs.

### MOB-002 — Required standalone Movies/TV watch routes are unreachable
**Severity:** P1  
**Category:** BUG, PLAYER, MOBILE  
**Confidence:** CONFIRMED  
**Platform/route:** Android; `/watch/movie/:id`, `/watch/tv/:id`  
**Component/file:** `AppMobile.jsx`, `AndroidVideoPlayer.jsx`

**Description / steps:** Open either required watch URL, or tap a Movies/TV watch action intended to navigate there. `AppMobile` has no watch pathname branch; unmatched routes render desktop `App`, whose `/watch/:type/:id` route mounts desktop `MovieWatch`, not the Android player.  
**Expected / actual:** Standalone Android player / desktop fallback player/layout or NotFound depending on type/auth.  
**Root cause/evidence:** The only mobile player component (`AndroidVideoPlayer`) has no import/use; `DramaDetailPage` retains an inline iframe player.  
**Impact:** Required route contract, deep links, player back behavior, state restoration, and phone layout are not implemented.  
**Recommended fix:** Implement native mobile watch route components and one canonical type contract (`movie`/`tv`).  
**Regression risk:** High; preserve episode/server/query URLs and protected access.

### MOB-003 — Movies/TV playback is embedded in details through untrusted iframe/proxies
**Severity:** P1  
**Category:** PLAYER, SECURITY, WEBVIEW  
**Confidence:** CONFIRMED  
**Platform/route:** Android Movies/TV details  
**Component/file:** `DramaDetailPage.jsx`, `mobile/api/adProxy.js`

**Description / steps:** Authenticate, navigate to a functional `DramaDetailPage` instance, then press Watch. The component replaces the details page with an iframe to providers such as Videasy/VidSrc/VidKing/Vidnest; ad-heavy providers are routed through public CORS proxies.  
**Expected / actual:** Separate, native-controlled player / details route becomes player; WebView loads third-party HTML through public proxies.  
**Root cause/evidence:** `showPlayer` condition returns iframe markup; player loading ends on iframe `load`, not playback readiness or stream health.  
**Impact:** Provider CSP/XFO/CORS failures yield false success/black content; fullscreen/back/episode lifecycle is not controlled by the app, and the product requirement is violated.  
**Recommended fix:** Move playback to MOB-002 routes; use validated direct media sources/native video component and explicit provider error states.  
**Regression risk:** High; test HLS, MP4, captions, no network, server change, next/previous and fullscreen.

### MOB-004 — Navigation guard blocks OAuth, mail return, sharing and external content
**Severity:** P1  
**Category:** SECURITY, AUTH, CAPACITOR  
**Confidence:** CONFIRMED  
**Platform/route:** All Android routes; OAuth/password reset/mail/share  
**Component/file:** `mobile/security/mobileNavigationGuard.js`, `mobile/main.jsx`

**Description / steps:** Trigger any external `<a>` or `window.open` (Google OAuth, opening email, a share URL, external player/support link). The startup guard cancels click propagation and replaces `window.open` with a null-returning function unless origin is one of four hard-coded internal origins.  
**Expected / actual:** Safe handoff through Capacitor Browser/app link / nothing opens.  
**Root cause/evidence:** The guard has no allowlist/action to `Browser.open`, no OAuth callback exception, and blocks `animevault://oauth` because it is not an allowed origin.  
**Impact:** Auth and recovery cross-app flows fail; links are silently inaccessible.  
**Recommended fix:** Replace blanket interception with strict URL validation plus Capacitor Browser/App APIs and explicit OAuth/deep-link handling.  
**Regression risk:** High; security tests must cover malicious schemes without blocking approved destinations.

### MOB-005 — Mobile password recovery cannot persist a sent recovery transaction
**Severity:** P1  
**Category:** AUTH, MOBILE, LIFECYCLE  
**Confidence:** CONFIRMED  
**Platform/route:** `/forgot-password` → `/set-new-password`  
**Component/file:** `mobile/pages/ForgotPasswordPage.jsx`, `pages/SetNewPassword.jsx`, `components/PublicPasswordRoutes.jsx`

**Description / steps:** Request a code; press Home/open mail; return after WebView/app recreation; open code entry. The mobile page holds email/status only in React state and never calls `savePasswordRecovery`. The shared recovery helper is only invoked after mounting Set New Password.  
**Expected / actual:** Recovery email/request timestamp survive return / state is lost and the user must re-enter email; no recovery record exists before navigating to code entry.  
**Root cause/evidence:** Two incompatible recovery flows exist; mobile page bypasses the shared persistence helper.  
**Impact:** The required mail-app return path is unreliable even before considering lifecycle recreation.  
**Recommended fix:** Persist only minimal recovery metadata immediately after successful request, with TTL, and restore/verify it in the dedicated flow.  
**Regression risk:** High; test cold start, process death, resend, expiry, logout, and mail deep link.

### MOB-006 — No Capacitor App lifecycle or hardware-back registration
**Severity:** P1  
**Category:** ANDROID, CAPACITOR, NAVIGATION  
**Confidence:** CONFIRMED  
**Platform/route:** All Android routes  
**Component/file:** `AppMobile.jsx`, `package.json`

**Description / steps:** Press Android system Back, background/reopen, lock/unlock, or receive a deep link. The app listens only for a browser custom event named `av-android-back`, but repository search finds no native code/plugin that dispatches it and no `@capacitor/app` listener.  
**Expected / actual:** Close overlay before route history; preserve/restore appropriate state / native default behavior is uncontrolled and the custom handler never fires.  
**Root cause/evidence:** `@capacitor/app` dependency is installed but not imported in mobile runtime.  
**Impact:** Back can close Activity/skip history; modal/player and recovery states are not lifecycle-aware.  
**Recommended fix:** Integrate `App.addListener('backButton'|'appStateChange'|'appUrlOpen')`, define ordered back handling, and persist only safe resumable state.  
**Regression risk:** High.

### MOB-007 — Cached user is treated as authenticated before validation
**Severity:** P1  
**Category:** AUTH, SECURITY, DATABASE  
**Confidence:** CONFIRMED  
**Platform/route:** App launch and all protected/shared screens  
**Component/file:** `api/UserContext.jsx`

**Description / steps:** Populate/retain `animevault_cached_user`, then restart offline, after session expiry, or after a remote logout. Provider initializes `user` from localStorage and immediately sets `authLoading(false)` when cached data exists; background restore failures do not clear it.  
**Expected / actual:** Signed-out/expired users are gated until validated / stale identity is displayed and user-data sync may run under it.  
**Root cause/evidence:** Cache acts as an authentication source and the Promise.race’s no-session result has no clearing branch.  
**Impact:** False-login UI and potential exposure/misassociation of cached profile/history requests.  
**Recommended fix:** Treat cache as display placeholder only; retain a `validating` gate until one authoritative session source confirms, and clear on negative/failed validation.  
**Regression risk:** High; test offline, token expiry, local logout, remote revoke, and multi-account changes.

### MOB-008 — Password-reset OTP is stored in localStorage
**Severity:** P2  
**Category:** SECURITY, AUTH, STORAGE  
**Confidence:** CONFIRMED  
**Platform/route:** `/set-new-password`  
**Component/file:** `pages/SetNewPassword.jsx`, `components/PublicPasswordRoutes.jsx`

**Description / steps:** Enter a six-digit OTP. Every email/OTP edit writes `{email, otp, requestedAt}` into `animevault_password_recovery` for up to 15 minutes.  
**Expected / actual:** OTP never persisted / reusable recovery secret remains in WebView local storage, accessible to same-origin XSS, backups and forensic/device access. Password itself is not stored.  
**Root cause/evidence:** `useEffect` calls `savePasswordRecovery({..., otp})`; helper serializes it.  
**Impact:** Reduces OTP confidentiality and creates stale-code reuse surface.  
**Recommended fix:** Persist only email/request timestamp, use backend-issued transaction state or secure native storage where needed, clear after every terminal error/success/expiry.  
**Regression risk:** Medium.

### MOB-009 — TMDB API credential is hard-coded into the mobile bundle
**Severity:** P2  
**Category:** SECURITY, API  
**Confidence:** CONFIRMED  
**Platform/route:** Search/home/details  
**Component/file:** `mobile/api/movies.js` (`TMDB_API_KEY`)

**Description:** A TMDB API key literal is compiled into the Android web asset and supplied as `api_key` in every request. The report intentionally does not reproduce it.  
**Impact:** Any APK recipient can extract/abuse the credential, exhaust quota, or attribute traffic to this project.  
**Recommended fix:** Use a restricted key/proxy with quota/rate controls; never regard `VITE_*` as secret.  
**Regression risk:** Medium.

### MOB-010 — Mobile CSP permits arbitrary origins and unsafe executable constructs
**Severity:** P2  
**Category:** SECURITY, WEBVIEW  
**Confidence:** CONFIRMED  
**Platform/route:** All Android WebView pages  
**Component/file:** `mobile/index.html`

**Description:** CSP sets wildcard `default-src`, `connect-src`, `img-src`, `media-src`, `frame-src`, `child-src`, and allows both `'unsafe-inline'` and `'unsafe-eval'` for scripts.  
**Impact:** CSP supplies almost no XSS/third-party frame defense; especially dangerous combined with localStorage auth/recovery data and untrusted iframe providers.  
**Recommended fix:** Adopt explicit origin allowlists, remove unsafe-eval/unsafe-inline with nonces/hashes, and narrow frame/media/connect sources.  
**Regression risk:** High; inventory all legitimate provider hosts first.

### MOB-011 — Public CORS proxies are used to load third-party player HTML
**Severity:** P2  
**Category:** SECURITY, PLAYER, API  
**Confidence:** CONFIRMED  
**Platform/route:** Movies/TV player  
**Component/file:** `mobile/api/adProxy.js`

**Description:** Ad-heavy embeds are URL-encoded through configurable/public CORS proxy services, with multiple public fallback endpoints. This neither strips response headers client-side nor guarantees provider compatibility.  
**Impact:** Playback reliability depends on third parties; proxies observe requested provider URLs and can change/serve content. It may also violate provider terms and introduces an open-proxy supply-chain dependency.  
**Recommended fix:** Remove public proxies; use a controlled backend only where legally authorized and validate origins/content.  
**Regression risk:** High.

### MOB-012 — Native ad-blocker patch is not applied by normal Android scripts
**Severity:** P2  
**Category:** ANDROID, CAPACITOR, CI/CD  
**Confidence:** CONFIRMED  
**Platform/route:** Local Android builds / generated native project  
**Component/file:** `package.json`, `scripts/patch-android-adblock.cjs`, `android-release.yml`

**Description / steps:** Run `npm run android:sync` or `android:build`. Neither runs `patch-android-adblock.cjs`; only the CI workflow invokes it. Generated `MainActivity` therefore lacks intended filtering in local builds.  
**Expected / actual:** Reproducible native configuration / CI and local artifacts behave differently.  
**Root cause/evidence:** Patch is a standalone workflow command, not an npm lifecycle step.  
**Impact:** QA cannot reproduce release networking/ad behavior; release parity is absent.  
**Recommended fix:** Make native generation/patch/sync one idempotent script and verify it in all Android build commands.  
**Regression risk:** Medium.

### MOB-013 — Ad-blocker patch may not compile against Capacitor’s WebView API
**Severity:** P2  
**Category:** ANDROID, CI/CD  
**Confidence:** LIKELY  
**Platform/route:** CI Android compilation  
**Component/file:** `scripts/patch-android-adblock.cjs`

**Description:** Generated Java calls `webView.getWebViewClient()`. `android.webkit.WebView` does not expose a public `getWebViewClient()` API in standard Android SDKs. The workflow verifies text presence only before Gradle compile.  
**Expected / actual:** Compile/retain Capacitor client / likely Java compilation failure unless a nonstandard extension is present.  
**Root cause/evidence:** Patch overwrites MainActivity and relies on an unavailable getter.  
**Impact:** Signed APK/AAB production job can fail.  
**Recommended fix:** Subclass/replace safely using Capacitor-supported hooks and compile the generated project in PR CI.  
**Regression risk:** High.

### MOB-014 — Media allow rule bypasses host blocking based on URL substring
**Severity:** P2  
**Category:** SECURITY, WEBVIEW  
**Confidence:** CONFIRMED  
**Platform/route:** Patched Android WebView  
**Component/file:** `scripts/patch-android-adblock.cjs`

**Description:** `isAllowedMedia` returns true when any URL contains `.m3u8`, `.mp4`, `.m4s`, `.ts`, `.vtt`, or `.webvtt` anywhere, before host blocking. A tracker/ad host can place such text in a path/query and bypass filtering. Conversely, media with extensionless signed URLs is not protected from host filtering.  
**Impact:** The stated filter guarantee is false; media behavior is unpredictable.  
**Recommended fix:** Parse URI path/content type, use a tested ordered policy and explicit allowlisted media origins.  
**Regression risk:** Medium.

### MOB-015 — Search reports provider/network failure as “No results” and lacks pagination
**Severity:** P2  
**Category:** API, UX, MOBILE  
**Confidence:** CONFIRMED  
**Platform/route:** `/search`  
**Component/file:** `mobile/pages/SearchPage.jsx`, `mobile/api/movies.js`

**Description / steps:** Disconnect network, exceed TMDB quota, or search valid content after a non-JSON/error response. `tmdbFetch` catches everything and returns null; Search converts it to `[]`, shows empty state, and never exposes retry/error. Search always calls page 1, despite API accepting page.  
**Expected / actual:** Clear offline/server error and paginated results / false “No results” with only first page.  
**Root cause/evidence:** Errors erased at API boundary; UI has no error/pagination state.  
**Impact:** Android WebView network failures are indistinguishable from genuine misses.  
**Recommended fix:** Typed result/error handling, abort/debounce request cancellation, retry UI, and pagination.  
**Regression risk:** Medium.

### MOB-017 — Profile-scoped data isolation is not established in mobile data flow
**Severity:** P2  
**Category:** DATABASE, PROFILES, ARCHITECTURE  
**Confidence:** LIKELY  
**Platform/route:** Profile switch, Library/Profile/History  
**Component/file:** `api/UserContext.jsx`, `AppMobile.jsx`, `mobile/pages/ProfilePage.jsx`

**Description / steps:** Switch “Who’s watching?” profile. Account switcher updates active subaccount, but UserContext’s sync effect is keyed only on `user?.id`; calls such as watch history/favorites/continue watching receive only the user ID.

## 6. Android / Capacitor Findings

`appId`, `appName`, `webDir`, HTTPS scheme and hostname match the declared Android package/domain. However `allowNavigation: ["*"]` is maximally permissive, conflicts conceptually with the JavaScript “block everything external” guard, and no configured StatusBar, SplashScreen, Keyboard, Browser, Filesystem, Preferences, App lifecycle, or deep-link plugin behavior exists. Android project generation is CI-only and local scripts fail before creation (MOB-018). The workflow injects an `animevault://oauth` intent filter after sync, but application code does not consume an app URL event (MOB-004/MOB-006).

## 7. WebView Findings

The app permits arbitrary frames/media/connect hosts and unsafe script execution (MOB-010). It uses iframe streaming and public CORS proxies (MOB-003/MOB-011), and lacks an Android WebView lifecycle/cookie/OAuth policy. The native patch does not configure JavaScript/DOM storage/cookies/mixed-content/media gesture/hardware acceleration itself; it assumes Capacitor defaults. Its attempted client replacement is likely non-compiling (MOB-013). The native filter blocks hostnames, but no request observability, certificate error policy, or graceful network UI exists.

## 8. Authentication Findings

MOB-004, MOB-006 and MOB-007 block reliable Android OAuth/session behavior. Auth depends on shared desktop `AuthModal` and several providers (Neon, proxy, legacy DB) raced together. The user cache includes an identity in localStorage, lacks documented expiry, and negative background restoration does not clear it. No actual Android OAuth callback listener exists despite generated URI scheme.

## 9. Password Recovery Findings

MOB-005 and MOB-008 apply. The mobile request page does not persist its successful transaction. The shared set-password page saves email **and OTP** in localStorage, 15-minute TTL, but does not bind it to backend recovery state or clear it on failure/back/navigation. Password values are not locally persisted. The reset then calls a legacy password synchronization after Neon reset; a sync failure is only logged, creating potential credential-store divergence.

## 10. Who’s Watching / Profile Findings

Profile picker is available only when a user exists, creates/switches subaccounts, and caps client-side display at five. Mobile profile state is vulnerable to user-wide data remnants (MOB-017). Reload/app recreation relies on shared context/localStorage rather than secure native storage. No audit evidence of backend ownership/RLS is present in the client repository; it must be validated against Neon schema/policies before production.

## 11. Homepage Findings

Home delegates to Movies/TV-oriented `DramasMoviesPage`, but card navigation is broken by MOB-001. The mobile shell delegates unmatched routes to desktop UI, so legacy Anime/Manga content can appear (MOB-016). API errors are generally swallowed into empty arrays; no reliable error/retry differentiation was established.

## 12. Search Findings

Search has a 300 ms debounce and cancellation flag, but does not abort fetches, uses only page one, swallows errors, and cannot open details due to MOB-001 (MOB-015). Input supports Android text entry but has no keyboard dismissal/focus management or URL-query persistence; pressing system Back is uncontrolled (MOB-006).

## 13. Details Page Findings

Movies/TV details are deterministically unreachable via their mobile route (MOB-001). When independently supplied props, details contain the player, directly violating the standalone player requirement (MOB-003). The component’s season fetch can duplicate: initial load fetches season and `details` update triggers the second effect to fetch it again. TV runtime is blank because only `details.runtime` is used (TV normally provides episode runtimes). Share/favorite controls required by scope are absent.

## 14. Player Findings

Standalone Android Movies/TV player routes do not exist (MOB-002). Details player is an iframe (MOB-003). AndroidVideoPlayer is unused and incomplete (MOB-022). Episode controls disable based on arbitrary `selectedEpisode <= 1`/`>= episodes.length`, which fails non-contiguous/numbered specials; source change does not retain server/episode in URL, so recreation loses state.

## 15. Scrolling Findings

**Actual scroll owner:** document/body in normal mobile shell; shell CSS explicitly sets visible/auto height for many desktop fallback elements at ≤700 px. No single confirmed root-level `overflow:hidden` preventing all page scrolling was found. Risks remain: drawer temporarily sets body overflow hidden, desktop fallback styles use fixed bottom nav/layout, fullscreen player uses fixed inset, and 100vh is widely used rather than consistently dynamic viewport units. These are architecture risks, not reported as confirmed universal scrolling failures. Manual device testing at 320/360/375/390/412/430 px is still required.

## 16. Schedule Findings

Mobile schedule merely renders shared `MediaSchedule`; no mobile-specific Movies/TV filtering or Thailand timezone configuration was found. Reminder bridge wording/links are Anime-only (`Anime is airing`, `/anime/:id`) (MOB-016). Reminder scheduling converts airing seconds ×1000 but no date/time-zone test implementation is present.

## 17. API Findings

TMDB direct calls expose a credential (MOB-009), ignore HTTP status and JSON parse errors, have no timeout/AbortController/rate-limit policy and erase failure into null (MOB-015). Streaming depends on unvetted embed hosts/public proxies (MOB-003/MOB-011). Query cache defaults to retry twice but imperative TMDB calls bypass React Query. No controlled API gateway is used for the content-critical mobile TMDB API.

## 18. Database Findings

Client has multiple auth/session/data implementations, increasing consistency risk. Cached identity pre-validation is MOB-007; subprofile partitioning is MOB-017. The repository provides client calls but not database migrations, Neon RLS policies, or server-side ownership checks, so IDOR/cross-user authorization cannot be proven safe from this checkout. This is a **coverage limitation**, not a claim that an IDOR exists.

## 19. Security Findings

Security findings: MOB-003, MOB-004, MOB-007, MOB-008, MOB-009, MOB-010, MOB-011, MOB-014 (eight findings; categories overlap). No secret values are reproduced in this report. `mobile/api/movies.js:TMDB_API_KEY` is an exposed API credential. There is no evidence in the audited checkout of a native JavaScript bridge beyond Capacitor plugins, but permissive CSP, localStorage secrets/identity and arbitrary third-party iframe content materially raise WebView risk.

## 20. Performance Findings

Desktop build emitted a 542.37 kB minified `MovieWatch` chunk (168.31 kB gzip) and Vite warned over its 500 kB limit; mobile bundle was not successfully verified due to MOB-019. Detail screen duplicates initial TV-season fetch. Search and home do not cancel actual fetches/abort stale requests; direct TMDB has no caching. HLS component cleans up Hls/event listeners correctly, but is unused. No app-state media pause/resume is implemented (MOB-006).

## 21. Accessibility Findings

MOB-021 applies. Positive observations: main menu/notification buttons provide aria labels and Search input has a label. Critical gaps remain drawer focus management, native modal semantics, reset form labels/associated errors, and tested visual focus/contrast on all pink/dark states. CSS reduced-motion support exists in selected mobile files but not established across all animated/shared screens.

## 22. UX Findings

The stated premium Movies/TV experience is undermined by blocked user journeys: card tap → error (MOB-001), Watch → embedded external player (MOB-003), system Back/lifecycle unspecified (MOB-006), and network error → misleading empty search (MOB-015). Drawer/profile controls are usable visually but no focus/keyboard/safe-area behavioral testing is automated. Settings labels still call it a “native-feeling anime experience,” another user-visible legacy inconsistency.

## 23. Anime / Legacy Contamination

**User-visible:** `/anime/:id`, `/manga/:id`, anime watch route, desktop fallback primary/bottom navigation, schedule reminder title/URL, profile/auth/settings language, and anime storage initialization. **Legacy bundled code:** allAnime/AniList/manga APIs, anime/manga pages/styles and shared desktop routes. **Potential Android build impact:** Mobile main imports shared desktop styles/UserContext/SubAccountGate and fallback `App`, so legacy code is not isolated/dead; route gaps actively expose it (MOB-016).

## 24. CI/CD Findings

MOB-012, MOB-013, MOB-018 and MOB-019 apply. Android workflow uses `npm install`, not deterministic `npm ci`; it validates several `VITE_*` values but Vite embeds these values in client assets, so they cannot be secrets. It deletes/generated Android, patches before sync (cap sync should preserve Java source but this ordering must be compiled/tested), and only greps source rather than running mobile verifier/Android instrumentation tests. There is no emulator/device smoke test for app launch, auth, player, deep links, Back or process recreation.

## 25. Release Findings

MOB-020 applies. Android release artifacts are signed only when secrets are configured and `apksigner verify` runs, which is positive. But Android and desktop build/release independently per push and publish separate tags/releases. VersionCode formula is deterministic for three-number semantic versions but assumes version always parses as `a.b.c` with integers. No single release contains all expected artifacts.

## 26. Dead Code

* `AndroidVideoPlayer.jsx` is production-bundled mobile code with no import/reference (unreachable).
* `mobile/api/allanime.js`, `anilist.js`, manga pages/styles, and multiple shared desktop anime routes are legacy in a Movies/TV product; they remain reachable due MOB-016.
* `seek` in `AndroidVideoPlayer` is defined but unused.
* `av-android-back` handler is unreachable without a native/browser event producer (MOB-006).
* `PublicPasswordRoutes` recovery persistence conflicts with mobile `ForgotPasswordPage` and is not used by `AppMobile` as its top-level dispatcher.

## 27. Missing Features

**BROKEN:** Movies/TV details, detail-to-watch journey, normal Android sync/build, verifier.  
**PARTIALLY IMPLEMENTED:** recovery persistence, profile isolation, Android player, deep link/OAuth configuration, ad blocking.  
**MISSING:** Android App lifecycle listeners, standalone movie/TV watch routes, controlled OAuth Browser return, player subtitle/progress/resume/server error UX, verified safe-area/keyboard handling, Android emulator smoke tests, one unified release.  
**UNREACHABLE:** `AndroidVideoPlayer`, custom Android back event.  
**FAKE UI / NO FUNCTIONALITY:** “Zen” mode simply changes iframe/proxy URL; iframe `load` is represented as player success without stream verification.

## 28. Cross-Screen Problems

1. **Route dispatcher split:** mobile custom paths and desktop fallback disagree (MOB-001/002/016).
2. **Lifecycle contract absent:** Back, process recreation, OAuth, mail return, player state and keyboard interactions lack Capacitor integration (MOB-004/005/006/021).
3. **Unsafe storage/auth contract:** cache and recovery secrets in localStorage plus permissive CSP (MOB-007/008/010).
4. **Third-party playback dependency:** iframe/public proxy/native ad filter policy conflicts (MOB-003/011/014).
5. **Build parity gap:** generation/patch/verification differ between local and CI (MOB-012/013/018/019).

## 29. Recommended Fix Order

1. **Stop release promotion and repair the route architecture**: define explicit mobile Routes for home/search/details/watch/auth and remove desktop fallback from Android. This unblocks MOB-001/002/016.
2. **Build a standalone Android player**: canonical movie/tv URL state, native media/HLS integration, back/fullscreen/lifecycle, direct provider authorization and errors. Then remove details iframe/proxies (MOB-003/011/022).
3. **Implement secure Android auth/recovery lifecycle**: Capacitor Browser/App callbacks, state gate, recovery transaction storage without OTP, cache validation/clear rules (MOB-004–008/010).
4. **Make Android builds reproducible and compile them**: reorder generation, incorporate idempotent patch, fix verifier/module type, compile Java and run emulator smoke tests (MOB-012/013/018/019).
5. **Enforce product/data quality**: remove user-visible anime legacy, profile-scoped backend contracts/RLS, API error/pagination, accessibility and device matrix testing (MOB-015–017/020/021).

## 31. Final Verdict

**Is the AnimeVault Android app production ready? No.**

Exact release blockers:

1. Movies/TV cards cannot produce a working detail screen (MOB-001).
2. Required standalone movie/TV watch routes are not implemented (MOB-002), and the existing player violates the separate-player requirement (MOB-003).
3. OAuth/external navigation and native app lifecycle/back behavior have no functioning Android integration (MOB-004/MOB-006).
4. Password recovery cannot reliably survive the mail-app lifecycle and stores OTP locally (MOB-005/MOB-008).
5. Cached identity may be treated as an authenticated session before validation (MOB-007).
6. Android local build and mobile verification are broken; native patch compilation is likely broken (MOB-013/MOB-018/MOB-019).
7. Release pipeline publishes separate Android and desktop releases (MOB-020).
